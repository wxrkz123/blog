用 AI 辅助写代码和做研究：能做什么、必须检查什么

大语言模型（ChatGPT、Claude、各种编程助手）已经成为很多人写代码、查报错、读文献的日常工具。它们确实能大幅提高效率：几秒钟写出一段读取数据、画图的代码，解释一条看不懂的报错，把 Stata 代码翻译成 Python。

但它们也会犯一类特别危险的错误：输出看起来完全正确，语气非常自信，实际上是错的。代码能运行，只是算错了；文献格式规范，只是根本不存在。这篇文章讨论怎样用好这些工具，以及哪些东西必须由你自己检查。

这个博客的一条原则是“文中所有代码的输出都是实际运行的结果”。这条原则在使用 AI 时更加重要。

一、AI 擅长什么

  • 写样板代码：读写文件、数据格式转换、画图的细节调整、正则表达式（正则表达式系列）、命令行参数的解析。这些代码有大量现成的写法，AI 写得又快又好，而且很容易检查；
  • 解释：解释一段陌生的代码在做什么、一条报错是什么意思、一个统计概念的直觉。用来学习新东西时，它是一个随时可以追问的助教；
  • 翻译：Stata 和 Python、R 和 Python、SQL 和 pandas 之间的翻译（实证研究工作流第 05 篇）；
  • 写测试：让它为你的函数写测试用例，包括你没有想到的边界情况；
  • 改写和润色：英文摘要的语法、术语的统一、长句的拆分；
  • 列清单：“这个回归还应该做哪些稳健性检验”“这类数据常见的问题有哪些”，作为头脑风暴的起点，再由你判断哪些真的适用。

这些任务有一个共同点：结果容易检查，或者错了代价很小。

二、AI 不擅长什么

  • 编造：不存在的函数参数、早已改名的 API、虚构的数据来源，最严重的是虚构的文献：作者、标题、期刊、年份、页码都很像样，但这篇论文根本不存在，或者内容和它说的完全不同；
  • 能运行但算错的代码：语法正确、没有报错、结果的数量级也合理，只是逻辑上有一个细微的错误（下一节的例子）。这比报错的代码危险得多；
  • 识别和推断的判断：这个变量能不能当工具变量、该在哪个层级聚类标准误、这个结果能不能解释为因果关系。AI 能讲出一套很专业的道理，但它不了解你的数据是怎样产生的，而且倾向于顺着你的说法给出肯定的回答；
  • 过时的知识：库的版本在不断变化，比如 pandas 3 中字符串方法的正则引擎和默认值（正则表达式系列第 03 篇），AI 给出的写法可能只适用于旧版本；
  • 数字：让 AI “估计”一个统计量、做一段心算，结果往往不可靠。数字要由代码算出来。

三、一个例子：看起来完全正确的代码

假设你让 AI 写一段代码：用股票的月度收益计算过去 3 个月的累计收益（动量信号），数据是长表格式，每行是一只股票一个月。它很可能给出这样的代码：

import numpy as np
import pandas as pd

def momentum_ai(df):
    """计算过去 3 个月（含当月）的累计收益。"""
    df = df.sort_values(["stock", "month"]).copy()
    df["mom3"] = (1 + df["ret"]).rolling(3).apply(np.prod, raw=True) - 1
    return df

代码简洁、有注释、能运行，按股票和月份排序这一步也做了。在真实数据上运行，得到的数字范围合理，没有报错。问题在哪里？

用一个答案已知的小例子测试它。构造两只股票、每只 4 个月的数据，手算出正确答案：

test = pd.DataFrame({
    "stock": ["A"] * 4 + ["B"] * 4,
    "month": [1, 2, 3, 4] * 2,
    "ret":   [0.10, 0.10, 0.10, 0.10, 0.0, 0.0, 0.0, 0.0],
})
expected = [np.nan, np.nan, 1.1 ** 3 - 1, 1.1 ** 3 - 1, np.nan, np.nan, 0.0, 0.0]   # 手算的答案
out = momentum_ai(test)
print(out.assign(expected=expected).round(4).to_string(index=False))
stock  month  ret  mom3  expected
    A      1  0.1   NaN       NaN
    A      2  0.1   NaN       NaN
    A      3  0.1 0.331     0.331
    A      4  0.1 0.331     0.331
    B      1  0.0 0.210       NaN
    B      2  0.0 0.100       NaN
    B      3  0.0 0.000     0.000
    B      4  0.0 0.000     0.000

股票 B 的前两个月应该是缺失值（不足 3 个月），实际上却算出了数：rolling 没有按股票分组，B 的窗口里混进了 A 的最后两个月。在真实的数据中，每只股票的前两个月都会借用上一只股票的收益，这些错误的值混在几十万个正确的值中间，几乎不可能被肉眼发现，却会污染每一只股票刚上市那几个月的信号。

正确的写法要在每只股票内部计算：

def momentum(df):
    df = df.sort_values(["stock", "month"]).copy()
    df["mom3"] = (df.groupby("stock")["ret"]
                    .transform(lambda r: (1 + r).rolling(3).apply(np.prod, raw=True) - 1))
    return df

out = momentum(test)
print("与手算的答案一致：", np.allclose(out["mom3"], expected, equal_nan=True))
与手算的答案一致： True

这个错误（忘记分组就做滚动或滞后的计算）在SQL 系列第 04 篇中也讲过，是人和 AI 都经常犯的错误。关键不在于 AI 会犯错，而在于一个 8 行的测试就能发现它。

四、核对 AI 输出的七条原则

  1. 代码一定要运行，结果一定由代码算出：不接受 AI 直接给出的数字；它说“结果约为 0.35”，你要自己运行代码看到 0.35。
  2. 用已知答案检验：手算一个小例子（如上一节），或者用模拟数据植入一个已知的效应，看代码能否把它找回来（金融实证系列第 06 篇就是这样检验事件研究的代码的）。
  3. 独立实现一遍：重要的结果用另一种方法独立计算，比如 SQL 和 pandas 各写一遍（SQL 系列第 04 篇），或者和教材、论文中的已知结果对比（计量进阶系列第 09 篇复现了原论文的数字）。
  4. 检查中间结果：每一步之后看行数、缺失值、描述统计，合并后检查键是否唯一（实证研究最常见的 20 个错误）。
  5. 每一条文献都要核对原文：找到这篇论文本身（通过 DOI、期刊网站、Google Scholar），确认它存在、作者年份正确、而且确实说了你引用的内容。绝不直接复制 AI 给出的参考文献列表。
  6. 不能解释的代码不放进论文：你需要能向审稿人解释每一行代码在做什么、为什么这样做。“AI 写的”不是理由。
  7. 记录过程：记下使用的工具和版本、关键的提示词和日期。AI 的输出会随版本变化，记录下来才能说明结果是怎样得到的（数据获取系列第 07 篇讨论了用 AI 做文本分析时的可复现性）。

五、怎样用得更好

  • 把问题拆小：“写一个函数，输入这样的 DataFrame，输出那样的结果”比“帮我做一个动量策略的回测”好得多。小问题的答案容易检查；
  • 给出上下文：数据的结构（列名、类型、前几行）、使用的库和版本、你已经尝试过什么、报错的完整信息；
  • 要求解释，而不只是答案：“为什么要这样写”“这里有哪些可能出错的地方”“还有什么其他写法”，让它的推理暴露出来，便于你检查；
  • 让它写测试：在写函数的同时，让它写出带已知答案的测试用例，然后你检查这些测试本身是否正确；
  • 先自己想，再问它：学习一个新方法时，先自己尝试写出来，再让 AI 检查或者对比。直接看答案学到的东西很少；
  • 对“肯定”保持警惕：如果你问“这个工具变量满足排他性约束吧？”，它很可能说“是的”。换成中性的问法：“这个工具变量的排他性约束可能在哪些情况下不成立？”

六、隐私与学术诚信

数据隐私：把数据粘贴进在线的 AI 工具，就是把它发送给了第三方。不要上传含有个人信息的数据、签了保密协议的数据（很多商业数据库的使用协议禁止这样做）、未发表的研究数据。需要 AI 帮助处理这类数据时，只描述数据的结构（列名、类型），用虚构的几行示例代替真实的数据；或者使用学校、单位批准的、在本地运行的工具。

学术诚信：很多期刊和学校已经制定了关于生成式 AI 的使用规定，常见的要求包括：AI 不能被列为作者；在论文中说明使用了什么工具、用来做什么；作者对论文的全部内容负责，包括 AI 生成的部分。投稿和提交作业之前，查看对应的规定。课程作业中是否允许使用 AI，以任课教师的要求为准。

小结

  • AI 擅长写容易检查的代码、解释、翻译、写测试和列清单；不擅长识别判断、最新的 API 和数字，并且会编造函数和文献。
  • 最危险的错误是能运行但算错的代码；用答案已知的小例子测试，往往几行代码就能发现。
  • 七条原则：代码要运行、用已知答案检验、独立实现一遍、检查中间结果、核对每一条文献、不放进看不懂的代码、记录过程。
  • 把问题拆小、给出上下文、要求解释、对肯定的回答保持警惕。
  • 不上传个人信息和保密数据；遵守期刊和学校关于 AI 使用和披露的规定。
